# Project Benchmark（立项对标）

给一个**已跑通、有家底**的项目做同赛道定位：先认清自己，再看竞品，最后落到"补什么、不补什么"。**对标是为了找差距与定位，不是为了照单全抄**。

## 前提

项目核心功能已跑通、且有测试或可验证产物作为"自家事实"。若连家底都盘不清，先回开发，不要进入对标——没底数的对标只会自我否定或盲目攀比。

## 工作流（按序执行）

### 1. 先盘自家事实（禁止跳过，禁止带着空白去调研）
- 读 README、跑测试、看目录结构与真实指标，把家底列成一条事实清单：测试数、eval 分数、已实现的差异化能力（证据引用、HITL、崩溃恢复、MCP 暴露等）。
- 每条自家事实必须能指到 `文件:行号` 或实跑命令输出；这是后面打分时"不自我否定"的锚。
- 教训警示：先有"175 测试、eval F1、HITL/证据引用"这些底数，对标时才知道哪些是真差距、哪些是玩具项目假装的优势。

### 2. 双路并行调研（每路 4-8 个真实仓库，宁缺毋滥）
- **A 路 · 同赛道竞品**：功能相近、解决同一问题的项目（如简历筛选对标 Resume-Matcher / pyresparser / resume-job-matcher / 中文 matcher / LangGraph 简历 Agent）。
- **B 路 · 工程/门面标杆**：不抢同一用户、但门面与交互值得抄的热门 Agent 产品（如 Dify / Langfuse / OpenHands / suna / assistant-ui / CopilotKit / vercel chatbot / agent-chat-ui）。
- 两路并行取证，不混为一谈：A 路回答"我比同类强在哪"，B 路回答"我的门面该长什么样"。

### 3. 取证纪律（红线：star/技术栈/license 严禁编造）
- 优先 GitHub API：`api.github.com/repos/{owner}/{repo}` 取 star/语言/license/最近 push。
- API 403/限流时，退用 raw README（`raw.githubusercontent.com` 不限流）+ 仓库 HTML 页交叉印证。
- 第三方统计站（starhistory 等）快照必须**标注取证日期与 ±误差**；抓不到的一律写"未核实"，绝不脑补数字。
- 每条事实附来源 URL；报告末尾分组列出，可回查。

### 4. 七维同表打分
- 七个维度：门面第一印象 / 前端视觉与 Agent 可观测交互 / 功能广度与产品闭环 / 架构与落地就绪 / AI 工程能力 / 工程化与可信度 / 社区与叙事。
- 本项目与每个竞品放同一张表打分（0-5），**评分锚点见 `references/dimensions.md`**，不凭感觉给分。
- 打分为每一分写一句依据（对应到具体仓库现象或自家 `file:line`）。

### 5. 诚实定位优势与差距
- 先写自家**真实差异化优势**（本项目实例：证据引用可回溯、HITL+崩溃恢复、真实简历 eval 对照、MCP 暴露、175 测试——这些优于多数玩具项目），不藏拙也不灌水。
- 差距分两个视角写：**"作品集门面所需"**（面试官一眼看到的东西）与 **"真实落地所需"**（客户真用起来才暴露的东西），二者优先级不同，别混。

### 6. 分层路线图 + 克制清单
- **P0 门面冲刺**（1-2 周可完成）/ **P1 体验升级** / **P2 落地深化**，每条带优先级与工时直觉、证据到 `file:line`。
- 同时给一份**"应保持不做"克制清单**：哪些对标项看着诱人、但会撑爆范围或偏离定位，明确写"不做"，防止对标变成无限膨胀。

### 7. 产出对标报告
- 结构、各节填写要点与本项目实例见 `references/report-template.md`。
- 本项目实例：`docs/competitive-benchmark.html`——单文件内联、墨青 `#1f5f54` 主色（不用紫蓝渐变）、雷达/漏斗/时间轴用手写内联 SVG，不引外部图库、不生成图片。

## 三条取舍原则

- **先有家底再对标**：没读自家代码就调研，是本项目踩过的坑——会拿玩具项目的缺点误判自己。
- **取证可核**：star/栈/license 只写查到的，抓不到标"未核实"，数字带取证日期。
- **对标服务于决策**：报告必须落到 P0/P1/P2 与"不做清单"，不是收藏一堆竞品链接。

## 参考文件（需要时再读，勿一次性全加载）

# Project Closeout（项目收束 / 作品集化）

把项目整理成「可运行、可演示、可协作、可信」的发布状态。**只做收尾，不新增功能**；不用门面掩盖功能缺口。

## 前提

核心功能已跑通、且有测试或可验证产物。若功能未完成或测试无法通过，先回到开发并向用户说明，不要进入收束。

## 工作流（按序执行）

### 1. 评估收尾就绪度（先判断，不动手改）
- 盘点：测试是否全绿、构建是否通过、功能是否闭环、有哪些可演示亮点。
- 给出二分结论：**工程层已就绪项 / 门面层仍缺项**。
- 明确回答"是否已具备收尾为可演示 demo 的条件"；缺口若是功能/正确性问题，停止收尾并上报。

### 2. 减法与归位
- 盘点根目录与各层散落文件（脚本、md、临时产物、输出目录）。
- 删临时冒烟/一次性脚本前，**全仓 grep 文件名、模块名、文档引用，确认零引用再删**。
- 保留有正式引用或工程价值的文件；说明类 md 做整合/更新/删除；根目录不堆半成品。
- 红线：不改业务代码逻辑；不碰 `.env`、密钥、含真实数据/PII 的目录，不入库。
- 不单独保留 `todo.md`/`REVIEW.md` 这类半成品：待办并入"已知边界"或转 issue 跟踪。

### 3. 协作入口（AGENTS.md 范式）
把面向"改代码的 AI / 未来的自己"的引导重写成**操作手册**（不是需求/设计文档）：项目目标与技术栈、目录职责、常用命令、架构与核心约定、**改代码规则**（测试全绿、新增配测试、数据红线、不破坏开关语义与数据访问边界）、评测/安全现状、已知边界与易错点。一切以源码为准，不凭记忆。

### 4. README 事实更新
- 徽章（CI / 测试数 / 许可证 / 技术栈）、一句话价值主张、**一条命令快速开始**、能力亮点、界面演示。
- 所有数字（测试数、指标、版本、star）与仓库实跑一致，**不虚报**。
- 保留原有优点，只更新事实与结构，不推倒重写用户认可的叙事。

### 5. 工程师导航（两节，缺一不可）
- **代码地图（精简版）**：按层列关键文件/类的职责与对外契约，再给一条端到端调用链。
- **参数键字典（完整版）**：全部配置项/环境变量列成「键 | 用途 | 默认值 | 出处 | 是否必填」，**逐条与配置源码核对**，不编造默认值。

### 6. 门面素材占位
- 截图、演示视频/GIF 由维护者补充；**不生成图片、不录屏**。
- 在 README 标注统一放置路径与文件名约定（如 `docs/screenshots/`、`docs/video/demo.gif`），留下图片引用占位。

### 7. 验证与交付清单
- 全量测试通过、构建通过、Markdown 结构与链接闭合、被删文件零残留引用、参数字典与源码一致、无真实 PII 泄露。
- 汇报：改动清单、验证结果、仍需维护者手动完成的动作（提交/推送、补素材、部署实测）。
- **默认不做 git commit/push**，除非用户明确要求。

## 三条取舍原则

- **减法优先**：根目录是门面，临时脚本与半成品文档要么归位要么删。
- **导航思维**：README 让访客 30 秒读懂架构，AGENTS 让协作者能动手，参数字典给配置真相——三者各司其职、不重复。
- **事实可核**：测试数、指标、默认值、文件引用全部以源码/实跑为准。

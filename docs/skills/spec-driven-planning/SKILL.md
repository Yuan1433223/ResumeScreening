# Spec-Driven Planning（需求规格化 / 阶段包规划）

把一句目标切成「可派工、可验证、可并行」的阶段包。**先写规格再动手；接口契约没冻结前不并行。**

## 前提

存在一个要落地的工程目标（功能 / 重构 / 加固 / 门面）。若方向本身还没判断"值不值得做、做哪段"，先回上游 project-benchmark 出路线图，再回到本技能切阶段包。

## 工作流（按序执行）

### 1. 澄清关键歧义
- 只问「会改变结论 / 范围 / 核心方案」的问题，一次问全（1–4 个）。
- 目标方向明确就用合理默认，不为问而问。
- 涉及文件 / 链接 / 账号用自由输入题，不给封闭选项。
- 例：本项目把"验证口径是否收敛到 pytest+build+冒烟""截图是否转用户自理"问清一次，后续派工不再反复。

### 2. 写阶段规格
- 每阶段含：目标 / 范围（做什么·不做什么双清单）/ DoD 完成定义（可验证）/ 验收标准 / 数据红线 / 依赖与前置。
- 数据红线随项目逐阶段重申（本项目：真实简历目录、eval/labels、`.env`、`data/` 绝不入库入镜）。
- 骨架见 `references/spec-template.md`；本项目实例为仓库根 `DEVELOPMENT_SPEC.md`。

### 3. 拆阶段包
- 每包独立可验证；按依赖排序：共享同一文件的改动串行，目录无交集可并行。
- 带工时直觉（如"测试护栏 0.5 天 / 前端新页 1 天 / 加固 1–2 天"）。
- **先冻结接口契约再并行**：本项目由主控先冻结 SSE / Dashboard / auth 契约，前后端子代理按契约并行。
- 判定矩阵与契约清单见 `references/phase-packing.md`。

### 4. 定义测试与验收口径
- 每个新功能配测试与编号批次（本项目 T1–T15）。
- 验证方式收敛到「全量 pytest + 前端 build + 必要时合成数据冒烟（不截图）」。
- 基线数字写死，如"175 不得退化"，不写"若干"。

### 5. 范围冲突处理
- 用户后续指令与既有规格冲突时，**以最新明确指令为准**。
- 显式说明"停止/不做"项与保留项。本项目多次收敛：截图/README 转用户自理、不 commit、代理端口仅网络失败时用。
- 越界产物（如子代理私写的 README 门面草稿）识别后清除或上报，不带着跑。

### 6. 派工与验收
- 自包含任务书：实体名 / 路径 / 契约 / 禁止项写全，不转发口语。
- 回收后**亲自重跑验证**，不只引用执行者自报数字。
- 冒烟发现口径缺陷要打回修根因。本项目漏斗 extracted 口径两轮修复：`count(runs)` 翻倍 → runs 去重 → assessments 去重，数字自洽才算完。

## 三条取舍原则

- **规格先行**：没冻结契约就并行，等于让两个子代理改同一个未定的边界。
- **可验证优先**：每个阶段包结束时必须有一条命令能判断"做完了没"。
- **最新指令优先**：规格是快照不是合同，用户一句话能推翻，但推翻要显式记录停做项。

01现状架构：一条串行的确定性流水线

已读过的源码：workflow.py / state.py / repository.py / scheduler.py / review.py / app/api.py / mcp_server.py

架构定位：这是一条规则优先、模型可选、一切副作用幂等+可恢复+可审计的确定性流水线。工程健壮性 9/10，但智能自主度 3/10、多智能体并行 3/10——你把 LangGraph 当"可检查点的 cron"用了，没用上它 Pregel/BSP 超步并行的核心能力。

02可深挖的点：源码里已经存在的技术债

这些不是"未来要做的新功能"，而是"现在代码里已经能看到、面试时会被追问"的点

技术债手写 CloudModelClient 重复造轮子

  • 当前自己实现了 HTTP 调 DeepSeek、重试、超时、错误映射。
  • LangChain 生态已有 BaseChatModel 抽象 + LiteLLM 网关，换模型=换实例，图/状态/checkpoint 全不感知。
  • 代价：你现在每加一个模型 Provider 要改 client；用了 LangChain 后 create_react_agent(model, tools) 直接吃 ChatModel 实例。

稳定性temperature=0 仍不精确复现

  • 跨运行 F1 从 0.67 波动到 0.88，7 份 dev 标注。
  • 根因：LLM 输出非确定性（batching/采样/服务端版本漂移），不是你的 prompt 问题。
  • 解法：建 golden set + 回归 eval，每次改 prompt 跑一遍；记录每次运行的 model version + seed + temperature。

业务模型转人工率 71.4% 偏高

  • 10 份里 7 份落到 needs_review，说明规则阈值和模型判断之间的"灰色地带"太大。
  • 可以深挖：是模型置信度低？还是 8 维评分的权重不合理？还是岗位画像太粗？
  • 方向：加一个 Critic 子智能体对 score 做 reflection，或者 LLM-as-judge 对比规则和模型的分歧点。

未用能力LangGraph BSP 并行被浪费

  • 当前 8 节点全串行，每个节点等上一个完成。
  • LangGraph 的 Pregel 引擎支持同一 super-step 多节点并行（_loop.py 82KB 核心）。
  • 立即可用：parse 后 extract/validate 可并行；score 阶段 8 个维度可并行打分再汇总。

可观测性无 tracing / 无结构化日志

  • 现在出问题只能翻 print 日志和 SQLite。
  • LangSmith / Langfuse 可以一键接入：每个节点的输入输出、token 消耗、耗时、错误率全链路可查。
  • 作品集加分项：README 里贴一张 LangSmith trace 截图，比说"我做了 observability"有力 10 倍。

上下文每次全量 prompt，无沉淀

  • 岗位画像、历史筛选决策、候选人画像每次都从数据库现查现塞 prompt。
  • 没有向量检索：相似历史简历、相似岗位 JD 没法语义召回。
  • 方向：岗位 JD 向量化 + 历史决策 embedding，screen 节点先 RAG 召回相似案例再打分。

03升级路线：四阶段，纵深 > 横铺

不要为了凑齐技术栈硬塞 Fine-tune / Distillation 等业务无关项。每个阶段都要有可演示、可量化的产出

PHASE 1

混合智能评估：模型建议 + 规则兜底 + Reflection

把 score 节点拆成 Extractor → Evaluator → Critic 子图：模型打分后 Critic 做一次自检（"这个结论有简历证据吗？"），分歧超阈值才转人工。同时接入 LLM-as-judge，用另一个模型对评分做复核。产出：转人工率从 71% 降到 40% 以下，F1 稳在 0.8+。

PHASE 2

记忆与检索：RAG + 向量库 + 长期记忆

岗位 JD、历史筛选决策、候选人画像全部 embedding 入库（Chroma / PGVector）。screen 节点先召回 Top-K 相似历史案例，再让模型基于"类比对标"打分。checkpoint 里加上跨会话记忆：同一个候选人重复投递时，系统记得上次为什么被 hold。产出：语义搜索 demo + 跨简历召回准确率指标。

PHASE 3

多智能体 + 对话式面试：用上 BSP 并行

把 8 维评分拆成 8 个并行子 agent（学历/经验/技能/稳定性/…），LangGraph 在同一 super-step 并行跑，barrier 后汇总。再加一个 Interviewer 子智能体：对模糊简历主动追问，通过 interrupt 等候选人回复——这正好用上 LangGraph 的人机在环能力。产出：并行加速比 + 多智能体拓扑图。

PHASE 4

开源工程化：Tracing / Docker / CI / 数据脱敏

接 LangSmith 全链路 trace；Docker Compose 一键起；GitHub Actions 跑 99 项测试 + lint；真实简历数据脱敏后开源示例。README 贴架构图 + trace 截图 + 评测数字。产出：可直接发给面试官的开源仓库。

04从 Pi 源码可借鉴的工程技巧

已读 Pi agent-loop.ts 全文 + harness/ 目录。不引入代码（TS→Python 不划算），只借设计思想，且 LangGraph/LangChain 生态已有对应实现

Pi 源码机制它解决什么问题你在 LangGraph 里怎么落地
transformContext
+ prepareNextTurn		 每轮 LLM 调用前压缩上下文，防止 context window 爆掉。Pi 把这做成了 hook，不是硬编码。 在每个长节点开头加一个 _compress_state()：把历史 tool result 摘要成一句话，只保留最近 N 轮原文。这就是"Context Engineering"的代码化。
beforeToolCall / afterToolCall hooks 工具执行前后可拦截、可修改结果、可 block。Pi 用它做权限检查和结果脱敏。 用 LangChain 的 @tool 装饰器 + wrapper 实现：调外部 API 前校验参数，返回后脱敏 PII（手机号/身份证）。
事件系统
（turn_end / tool_execution_*）		 Pi 把 agent 运行的每个节点都发出事件，UI/telemetry 订阅即可。 LangGraph 的 stream_mode="updates" + LangSmith 自动事件埋点。你不用自己写事件总线，接上就有。
steering / follow-up 队列 用户在 agent 运行中插话，Pi 把消息排队，下一轮注入。 LangGraph 的 interrupt() + Command(resume=...) 已覆盖：review 节点暂停等人工回复，回复后继续。你已经在用了。
compaction/ 目录 Pi 把上下文压缩做成独立模块，可插拔（摘要式 / 截断式 / 选择性保留）。 Phase 2 做 RAG 时，compaction 策略 = 召回哪些历史片段塞进 context。Pi 的 compaction 接口设计可直接抄。
skills.ts（13KB） Pi 把工具按 skill 分组，可按需加载，不是一次性塞 50 个工具给模型。 用 LangGraph subgraph 实现：不同岗位类型加载不同工具子集（技术岗 vs 销售岗工具不同）。也对应 MCP 的 server 分组。
telemetry.ts（18KB） Pi 自己实现了 token 计数、耗时、错误上报。 不要自己写。LangSmith / Langfuse / OpenTelemetry 现成，接 langsmith SDK 两行配置。
关键判断：Pi 值得抄的是"hook 化的上下文管理 + 工具管道 + 事件驱动"这三个设计思想，不是代码本身。LangGraph/LangChain 生态里 90% 已有对应实现，你要做的是"知道它们存在 + 在正确节点用上"，而不是重写一遍。

05LangChain / LangGraph 生态可引入清单

按"替换你现在的什么"来列，不是按技术名词堆砌

替换手写 client

  • langchain-openai / langchain-deepseek ChatModel
  • LiteLLM 统一网关（100+ Provider 一个接口）
  • 收益：换模型改一行配置

加评估子智能体

  • create_react_agent(model, tools)
  • 把 Critic / Interviewer 做成子图
  • 收益：评估逻辑可独立测试

加 RAG / 向量库

  • langchain-chroma / pgvector
  • RecursiveCharacterTextSplitter
  • OpenAIEmbeddings / 本地 bge-m3
  • 收益：语义召回相似案例

加可观测性

  • langsmith SDK（官方）
  • Langfuse（开源自托管）
  • OpenTelemetry 标准
  • 收益：trace 截图放 README

加 Eval

  • LangSmith Evaluations（dataset + annotate）
  • 自建 golden set（你已有 7 份）
  • 回归测试每次跑
  • 收益：改 prompt 不再靠玄学

加 MCP（可选）

  • 把 ATS / 岗位库 / 简历源做成 MCP server
  • LangGraph 原生支持 MCP client
  • 收益：工具可跨 agent 复用

06优先级矩阵：下一步先做什么

按"对作品集价值 × 实现成本"排。先做右上，最后考虑左下

★ 现在就做 · 低成本高价值

  • 接 LangSmith tracing（2 行配置）
  • 用 LangChain ChatModel 替换手写 client
  • 建 golden set + 回归 eval（已有 7 份标注）
  • 把 score 节点的 8 维改成 BSP 并行

下一步 · 中成本高价值

  • 加 Critic 子智能体（reflection + LLM-as-judge）
  • Chroma 向量库 + 岗位 JD 语义召回
  • Docker Compose + GitHub Actions CI

以后再说 · 高成本中价值

  • 对话式面试子智能体（interview 场景）
  • MCP server 封装 ATS 对接
  • 多模态简历解析（扫描件 OCR 增强）

不建议做 · 对作品集无增益

  • Fine-tune / Distillation（简历场景用不上）
  • 引入 Pi 代码（TS→Python 不划算）
  • 自己写 agent loop（LangGraph 已够用）
  • 自己写 telemetry（LangSmith 现成）
一句话总结：你现在的项目是一条"工程严谨但智能度有限"的串行流水线。升级方向不是堆技术名词，而是在已有骨架上注入三个东西——子智能体（智能化）、RAG 记忆（上下文工程）、tracing+eval（可验证）。Pi 教你的是 hook 化的设计思想，LangGraph 给的是 BSP 并行 + checkpoint 的执行引擎，LangChain 给的是 ChatModel 抽象和工具生态。把这三层接对，就是一个能讲清 tradeoff 的优质作品集。
